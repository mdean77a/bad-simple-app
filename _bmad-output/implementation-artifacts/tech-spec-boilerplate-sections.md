# Tech-Spec: Boilerplate Sections for Conditional and Signature Pages

**Created:** 2026-03-01

## Overview

### Problem Statement

Conditional sections (Genetic Research, Sample Storage, HIV Testing) and signature sections (Adult Consent, Teen Assent, Parent/Guardian Permission) are currently generated by the LLM, but their content is standardized boilerplate that doesn't require AI generation. This wastes LLM calls, adds unnecessary latency, and introduces variability where none is wanted.

### Solution

Store boilerplate text directly in `section_definitions.py`. When the user confirms the outline and sections begin generating, conditional and signature sections populate instantly with their boilerplate text instead of going through the LLM pipeline. Users can still approve and edit these sections, but the Regenerate option is removed since the content was never LLM-generated. The backend also guards the regenerate endpoint against boilerplate sections.

### Scope

**In Scope:**
- Add `boilerplate_text` field to all 6 conditional and signature section definitions in `section_definitions.py` (placeholder strings for now)
- Backend: skip LLM generation for sections that have boilerplate; return them instantly as "ready"
- Backend: guard the `/sections/regenerate` endpoint to reject boilerplate sections
- Frontend: hide the Regenerate button on SectionCard for boilerplate sections
- Frontend: boilerplate sections appear immediately on the dashboard (no streaming needed)
- Frontend: persist `category` through project file save/load

**Out of Scope:**
- Actual boilerplate content (placeholder text only — user will fill in later)
- Changes to outline generation (LLM still decides which conditional/signature sections to include)
- Changes to standard sections (still fully LLM-generated)
- Visual redesign of section cards
- Export changes (see Known Limitations in Notes)

## Context for Development

### Codebase Patterns

**Backend generation flow:**
1. Outline page confirms → POST to `/sections/generate` with `{protocolId, sections: [{id, name}]}`
2. `stream_sections_parallel()` builds a LangGraph StateGraph with one node per section
3. Each node: RAG search → build prompt → stream LLM tokens → emit SSE events
4. SSE format: `section_start` → `section_chunk` (token-by-token) → `section_complete`

**Frontend consumption flow:**
1. `handleConfirm()` in outline page creates `SectionState[]` all with `status: "generating"`, empty content
2. Navigates to dashboard; `useSectionStreaming` hook detects "generating" sections
3. Hook calls `streamSections()` SSE client → updates section content/status via `updateSection()`
4. SectionCard renders content with Approve / Edit / Regenerate buttons

**Key types:**
- `SectionDef` (backend): `frozen=True` dataclass with positional fields `name`, `detection_guidance` — new fields with defaults MUST come after these
- `OutlineSection` (frontend): has `category: "standard" | "conditional" | "signature"` — but category is NOT carried into `SectionState`
- `SectionState` (frontend): `id`, `name`, `content`, `status`, `originalPrompt`, `approval?` — no category field
- `ALL_SECTIONS` (backend): `list[tuple[str, SectionDef]]` — each entry is `(category_string, SectionDef)`. Any helper iterating this must unpack tuples correctly.

**Serialization flow:**
- `serializeProject()` in `projectFile.ts` (lines 91-127) explicitly maps `id`, `name`, `content`, `status`, `originalPrompt`, and `approval` — new fields on `SectionState` will be **silently dropped** unless explicitly added here
- `deserializeProject()` (lines 133-154) reconstructs `SectionState` from `ProjectFile` — new fields must be explicitly included or they will be absent on reload
- `validateProjectFile()` validates section fields — `category` is optional so no validation change needed

**Regenerate flow:**
- SectionCard's Regenerate button opens `RegenerateModal` via `setRegenSection(section)` in dashboard page
- Submit calls backend `/sections/regenerate` SSE endpoint
- `stream_section_regenerate()` does RAG + LLM revision
- **No server-side guard** currently prevents regeneration of any section by name

### Technical Decisions

1. **Backend is source of truth for boilerplate content.** `section_definitions.py` stores the text; the backend emits it instantly via SSE (same event format, just no LLM delay). This was chosen over having the frontend populate boilerplate directly in `handleConfirm()` because: (a) it keeps content management in one place on the backend, (b) the frontend doesn't need to know or bundle boilerplate text, and (c) the SSE flow is already battle-tested. The trade-off is an unnecessary network round-trip for pre-known static text, but the latency is negligible (no LLM call) and the architectural simplicity is worth it.

2. **`boilerplate_text: str | None = None` on SectionDef.** This field MUST be placed after `name` and `detection_guidance` on the frozen dataclass because those fields have no defaults — placing a defaulted field before them would break all existing positional instantiations. Presence of a non-None value is the indicator for boilerplate — no separate boolean needed. `get_boilerplate(name)` helper enables lookup by section name.

3. **`category` field added to `SectionState` and persisted.** Carried from `OutlineSection.category` through `handleConfirm()`. Used by SectionCard to hide Regenerate button. Persisted via explicit updates to both `serializeProject()` and `deserializeProject()` in `projectFile.ts`. Optional field (`?`) — legacy project files without it default to showing Regenerate (backward compatible). No `ProjectFile` version bump needed because: (a) the field is optional and additive, (b) `validateProjectFile()` accepts unknown section fields, and (c) old code reading a new file will simply ignore `category`.

4. **SSE flow unchanged for boilerplate.** Backend emits `section_start` → `section_chunk` (full content in one chunk) → `section_complete` for boilerplate sections, then runs LangGraph for standard sections. Frontend processes both identically via `useSectionStreaming`. The hook's existing `startedRef` guard and error handling apply to the combined stream. Note: if the SSE connection drops after boilerplate events but before LLM completion, the LLM sections will be stuck in "generating" — this is a pre-existing limitation of the hook's reconnection logic, not introduced by this change.

5. **Backend guards regeneration of boilerplate sections.** The `/sections/regenerate` endpoint checks `get_boilerplate(sectionName)` and returns a 422 error if the section is boilerplate. This is defense-in-depth — the frontend hides the Regenerate button, but the backend independently prevents regeneration via direct API calls or race conditions.

### Known Limitations

- **Placeholder text in exports:** Until the user replaces placeholder boilerplate text with real content, exported PDF/DOCX/Markdown files will contain strings like `"[Boilerplate placeholder for Genetic Research]"`. This is expected since actual boilerplate content is out of scope for this spec.
- **SSE round-trip for static content:** Boilerplate sections route through the SSE pipeline even though their content is pre-known. This adds a negligible network round-trip but keeps the architecture simple — the backend remains the single source of truth for all section content.
- **No SSE reconnection for partial failures:** If the SSE connection drops after boilerplate events are emitted but before LLM sections complete, the LLM sections will be stuck in "generating" with no automatic retry. This is a pre-existing limitation of the `useSectionStreaming` hook, not introduced by this change.
- **Brief skeleton flash for boilerplate sections:** Because boilerplate sections start with `status: "generating"` and empty content (same as standard sections), they will briefly show the skeleton loading animation until the SSE response arrives. The SSE response is near-instant (no LLM latency), so the flash is typically imperceptible. This is an accepted trade-off of routing boilerplate through the SSE pipeline (Technical Decision #1) rather than pre-populating in `handleConfirm()`.

### Notes

- The outline generation flow is unchanged — the LLM still decides which conditional/signature sections to include based on protocol analysis
- Placeholder boilerplate text will be replaced with real content by the user in a follow-up — this spec only establishes the plumbing
- If `llm_sections` is empty (all selected sections are boilerplate), the backend returns without initializing an LLM model — significant performance optimization for that edge case
- Boilerplate sections use the exact same SSE event format as LLM sections — the frontend's `useSectionStreaming` hook processes both identically with no special handling needed
